# Personal-map opening measurement

This is an aggregate first-party measurement beginning only at explicit owner activation. It does not reconstruct prior usage, identify unique people or prove a trip occurred.

An opening is a successful visible map render after route context, canonical place scripts and private album state load successfully. The map client sends one same-origin POST per document after rendering, including CSRF and a server HMAC token bound to the authenticated account, canonical route and current session CSRF. Background context/media/album requests, hidden tabs, denied access, missing routes and initial password-change pages do not count. Opening the journal alone does not count. The server revalidates the existing account session, role and map approval on every request. Client-supplied role, account or route assertions cannot override this identity.

All openings for one account and canonical map within a fixed 30-minute window from its last counted opening are combined, across reloads and concurrent sessions. First and last times are those of the counted openings. There is no polling, heartbeat or periodic reopening of an idle tab. Returning to a still-open document does not create another count; a later document opening after the window can count. A family sharing one account is not multiple unique visitors.

Owner-admin activity has its own counter and never increases the customer counter, including when an owner opens an existing customer map. Demo/test map exclusions are selected by an existing authenticated owner at activation. The server resolves selected accounts to their current canonical map scope and saves that classification privately, without changing user or route records. This initial classification is not accepted from a customer flag. New test-only accounts must be excluded before production use; do not test using customer credentials. Public demo pages do not call this authenticated measurement endpoint.

Storage is beneath the existing non-public `personal-trips-private/map-usage` directory, mode0700; data and lock files mode0600. Activation contains only version, UTC epoch start time and hashed excluded scopes. Each fixed-size scope file contains only version and three counters with first/last UTC epochs. The scope filename is SHA-256(account key + canonical reference). No IP, user agent, browser/session fingerprint, contact details, photos, album entries, itinerary or event log is added. Existing authentication/rate-limit/audit mechanisms remain unchanged. Concurrent writes use per-scope exclusive locks and mode0600 temporary files followed by atomic rename. Corrupt or unavailable storage reports unavailable, never a zero-use claim, and does not block map use.

## Deployment and rollback

1. Coordinate the live writer and take a fresh private backup of only changed server files. Compare live source to the reviewed base and merge any intervening changes first. Do not overwrite customer files, sessions, albums, approval gate, owner roles or unrelated manifest hashes.
2. Install `map-usage.php`, `index.php`, `album-api.php`, `owner-admin.php`, `album-bootstrap.js`, `trip-album.js`, and the merged `album-assets.json`. The new include must be installed before callers, and the manifest last. Existing public map catalogs are unaffected.
3. In existing authenticated Personal maps owner view, check only the actual known demonstration/test map(s), then choose Start measuring map openings. This idempotently records the real activation time. Do not backdate it or infer usage from trip dates.
4. Confirm owner list shows activation time and truthful zero-observation wording. Snapshot private counters before/after an owner-admin map render and confirm customer counts do not increase. Use synthetic accounts only for customer-path live verification, and provision them under the existing authorized test procedure if explicitly available; never reset customer credentials for this test.
5. Roll back the seven application files from the fresh backup, preserving the new private measurement directory. Never restore users, routes, albums or sessions as part of this feature rollback. Resuming the feature uses the existing activation time and counts, not a fabricated new baseline.

Synthetic Python integration tests exercise authorization, canonical scope binding, owner/demo separation, fixed-window boundary, concurrent atomic updates, data minimization, failure behavior and unchanged accounts. JavaScript tests cover visible-only acknowledgement and duplicate renders. Existing album, owner-access and request-approval tests remain required.
